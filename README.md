# Microbloggr

A local Astro microblog editor. The standalone demo lives in [microbloggr-demo](https://github.com/jyoungblood/microbloggr-demo).

See the [publishing roadmap](docs/publishing-roadmap.md) for guided installation, the public demo, and the first npm release.

## Package development

Use Node 22.22 or newer. This package targets Astro 7.4.0. `npm run dev` starts the shared playground using local package source.

```sh
npm install
git clone https://github.com/jyoungblood/microbloggr-demo.git playground # If not already present.
npm --prefix playground ci
npm run dev
```

The terminal prints the active URL, normally `http://127.0.0.1:4321`.

Running `npm run dev` inside `playground` has the same behavior. Package and demo edits appear in that shared dev server. Run `npm run dev:fixture` to use the isolated test site without the demo checkout. Demo builds always use its installed, pinned package; `npm --prefix playground run dev:package` previews that installed version locally.

- `/editor` opens Microbloggr. The Astro toolbar also has a Microbloggr button.
- `/editor/archive` shows all sample posts with search and filters.
- `/` shows the separate public theme. Only published posts appear there.

Create and edit all five post types, save drafts, publish locally, backdate posts, and delete to recoverable trash. The editor is rich text saved as Markdown, with keyboard undo/redo, local uploads, and provider playback.

## Seed content

The test site includes 16 Markdown posts across six months, including three drafts and every post type. All four supported providers have examples.

Local artwork and a short synthesized WAV file are original fixtures generated by `scripts/seed.mjs`. Feed cards and detail pages load recognized provider players. The Bandcamp seed uses an ordinary album link; saving it in the editor resolves its player.

```sh
npm run seed        # Add missing sample files without changing existing files.
npm run seed:reset  # Replace only known sample posts and media.
```

Reset replaces edits to sample posts with IDs beginning `08c0ffee-2026-4000-8000-`. It leaves all other posts and media untouched. It never clears a directory.

You can edit the Markdown files directly in `tests/fixtures/site/src/content/microblog`. Astro reloads the collection. The schema belongs to the test site at `tests/fixtures/site/src/microblog.schema.ts`.

## Local package setup

The package lives at this repository root. The test site imports its source directly. The separate demo installs the actual package from a pinned GitHub commit until npm publication.

To run the demo:

```sh
git clone https://github.com/jyoungblood/microbloggr-demo.git
cd microbloggr-demo
npm ci
npm run dev
```

```js
// astro.config.mjs
import { defineConfig } from "astro/config";
import microbloggr from "microbloggr";

export default defineConfig({
  integrations: [microbloggr({ editorPath: "/editor" })],
});
```

`editorPath` is relative to the Astro `base`. For example, base `/garden/` and editor path `/write` produce `/garden/write`.

The collection is named `microblog`. Optional configuration:

```js
microbloggr({
  editorPath: "/editor",
  contentDir: "src/content/microblog", // Relative to the project root.
  mediaDir: "assets/microblog", // Relative to Astro's publicDir.
  uploadLimits: {
    photo: 20 * 1024 ** 2,
    audio: 100 * 1024 ** 2,
    video: 100 * 1024 ** 2,
  },
});
```

Match `contentDir` in the collection's glob loader. Directory paths must stay inside the project and cannot contain symlinks. Posts use a flat directory of stable ID filenames. Forms display dates in the browser's local timezone; the archive and feed use UTC.

For another project, copy `templates/microblog.schema.ts` and the playground collection definition into its `src` directory. Merge the collection definition with existing collections. The copied schema has no dependency on Microbloggr.

Optional schema fields and defaults are editable. Saves preserve custom frontmatter, but custom fields do not create editor inputs. The save API validates the core post format; Astro validates your copied schema on content load/build. New required custom fields need defaults or manual edits. Renaming core fields breaks compatibility.

## Production boundary

The editor route, toolbar entry, and virtual module register only for `astro dev`. The integration adds nothing to `astro build`, `astro preview`, or `astro sync`.

Editor requests require a loopback connection, a local host, and no forwarded headers. Cross-origin requests are rejected. Every write and upload request also requires a random token for the current dev session. Mutation endpoints exist only under the editor URL during dev.

The public theme has its own components and CSS. It imports no editor UI. Its index and detail routes filter for `status === 'published'`.

Files in `public` still enter the static build, including attachments for drafts. Draft status does not make media private.

## Editing and recovery

- Save draft and Publish write Markdown locally. Publish does not deploy, commit, or push.
- Metadata-only edits keep the Markdown body verbatim. Rich edits may normalize supported Markdown formatting. Tables, images, raw HTML, task lists, and other unsupported rich syntax stay in source mode.
- A stale save or delete is rejected. Copy your unsaved changes before reloading a post changed on disk.
- File changes show a reload notice within five seconds in a visible tab, or when you return to the tab. Changed, removed, and unreadable posts get specific notices. Notifications never replace form fields or accept a new revision; your own saves do not trigger an external-edit notice. Astro's wildcard content reloads are deferred inside the editor so edits stay in place.
- Opening a post from the archive retains its filters and page. Close, Back to archive, and deletion return there; the tab restores the saved scroll position and card focus where possible. Browser Back also retains the archive context. Storage-disabled browsers keep normal browser history behavior.
- Dirty forms warn before navigation. Unsaved edits are not cached or autosaved; leaving a form discards them.
- Delete moves the exact Markdown file to `.microbloggr/trash/<original-id>-<trash-uuid>.md`. The editor's Trash page (linked from the sidebar) restores posts under their original IDs or deletes them forever, one at a time or several at once with the checkboxes and Select all. Deleting forever also deletes the post's media files unless another post or trashed post uses them. A restore never overwrites an existing post with the same ID.
- `.microbloggr/` holds its own `.gitignore`, so trashed posts stay out of your site's Git history. Media used by trashed posts stays in `public/` and ships with builds until the trash is emptied.
- Picked files upload only when the post is saved. Removing a photo or media file from a post deletes it from the media folder on save, unless another post, draft, or trashed post still uses it. Deleting a post keeps its media so the trashed post can be restored.

Photos accept JPEG, PNG, WebP, GIF, and AVIF. Audio accepts MP3, M4A, WAV, and Ogg/Opus. Video accepts MP4 and WebM. File signatures and size limits are checked; playback depends on browser codecs. Uploads use generated filenames, not the original filename.

Photo, video, and audio forms start with two choices: upload a file or add one from the web. The whole area is also a dropzone. Photo posts support up to 100 images in a thumbnail grid: drag to reorder (the first photo is the cover), and use the circled x to remove one. Video and audio show their player with the same x; removing it brings the choices back. Links to images and media files are downloaded into the media folder on save, while YouTube, Vimeo, SoundCloud, and Bandcamp links stay as embedded players. Links to local or private network addresses are refused. A failed upload or download stops the save and keeps everything that succeeded.

Uploaded files live under `public/assets/microblog/<type>` by default and are publicly included in builds, even for drafts.

For importers, see the [photo post format](docs/photo-format.md). Photos use an ordered array with stable IDs and URLs. Old files without photo IDs remain valid. Saves assign missing IDs and preserve custom photo metadata by identity.

## Provider playback

Choose **Provider link** as the audio/video source type. Feed cards and detail pages share the same player adapters:

- **YouTube:** watch, youtu.be, Shorts, live, and embed URLs.
- **Vimeo:** video and player URLs, including unlisted links with their privacy hash.
- **SoundCloud:** full track and playlist URLs, including secret links. Short share links remain clickable fallbacks; use the full destination URL for playback.
- **Bandcamp:** an album or track page link (`https://artist.bandcamp.com/album/…`), or a `https://bandcamp.com/EmbeddedPlayer/…` URL from Share/Embed. On save, the editor reads a page link’s album or track ID and stores the player URL in `media.embed`, next to the original link. Custom artist domains stay links.

For the seeded Tycho album, the player URL is `https://bandcamp.com/EmbeddedPlayer/album=3619628392/`. [Bandcamp embed instructions](https://get.bandcamp.help/en/articles/15263071-how-do-i-create-a-bandcamp-embedded-player)

Posts retain the entered URL in `media.src`; generated iframe HTML is never stored. Players start paused and ignore supplied playback options. A recognized player shows alone; unsupported links show a plain link instead. Providers may still restrict playback by privacy, region, or embed settings.

Saving a video or audio post also stores an image in `media.poster` when it has none: YouTube and Vimeo thumbnails, SoundCloud and Bandcamp artwork. Images are downloaded into `<mediaDir>/thumbnails/`; uploaded and direct video files get a frame captured in the browser. Embedded players show their own artwork, so feed cards use these images only for archive tiles and audio files. A generated thumbnail is replaced when the video source changes; a poster you set yourself is never touched.

Only on save, the dev server contacts YouTube, Vimeo, SoundCloud, and Bandcamp for thumbnails, artwork, and Bandcamp player IDs. A failed lookup never blocks a save. Set `providerLookups: false` to keep the editor fully offline. The browser loads players directly from the provider. Public themes own their embeds; these adapters only run in the editor. See [provider implementation notes](docs/provider-playback.md).

## Checks

```sh
npm test                  # Persistence, uploads, Markdown safety, and local access checks.
npm run check             # Astro and TypeScript diagnostics.
npm run test:integration  # Actual dev, build, and preview checks over HTTP.
npm run build
npm run preview
```

The integration check uses a temporary copy of `tests/fixtures/site`. It exercises saves, publication, uploads, trash, tokens, custom paths, a non-root base, and production exclusion. DOM checks exercise rich text, the Markdown fallback, undo/redo, tags, saves, and conflict recovery without launching a browser. It builds before and after dev sessions and closes its temporary servers afterward.

Visual checks remain manual. Open the feed, archive, a detail page, and the editor at desktop and mobile widths. Try typing, pasting, keyboard navigation, uploads, and publication controls.
